## 1. 目标

建立两条清晰、可验证的数据库路径：

1. **全新环境**：从空 SQL Server 一次性创建与当前代码匹配的完整数据库。
2. **历史环境**：只补齐缺失结构，不覆盖、不删除现有业务数据。

最终应消除“当前电脑能运行，但换电脑或部署服务器后缺表、缺字段”的 P0 风险。

## 2. 本轮边界与安全说明

本轮已完成：

- 只读扫描数据库 SQL 文件、数据模型和代码中的 SQL。
- 只读查询当前数据库的表、字段、索引、外键和行数。
- 只读统计重复键、孤儿记录和 Stage 11 历史现状。
- 形成差异结论和后续实施方案。

本轮未执行：

- 未创建、修改或删除数据库对象。
- 未插入、更新或删除任何业务数据。
- 未修改现有 `Setup.sql` 或升级脚本。
- 未创建临时数据库。
- 未移除程序中的运行时 `Ensure...` 兜底逻辑。

## 5. 已确认的 P0：全新建库不可复现

### 5.1 `Setup.sql` 存在直接语法错误

`StoryboardFrames` 的最后一个字段 `EndScene` 后保留了逗号，紧接右括号。SQL Server 会使该建表批次失败，导致分镜表和后续依赖处于不确定状态。

严重程度：**P0（全新环境建库阻塞）**。

### 5.2 `Setup.sql` 缺少 6 张当前代码依赖的表

- `Dramas`
- `ReferenceAssets`
- `VideoGenerationTasks`
- `VideoStyles`
- `TokenUsageConfig`
- `Works`

其中 `Dramas` 没有统一的运行时建表兜底，新库只执行 `Setup.sql` 后，漫剧和项目链路会直接失败。

严重程度：**P0（核心功能不可用）**。

### 5.3 `Setup.sql` 中已有表仍缺少大量当前字段

重点差异：

| 表 | `Setup.sql` 缺少的当前字段 |
|---|---|
| Projects | DramaId、CurrentBatch、CoverImage、StyleId、VideoRatio、VideoWatermark、VideoAudio、VideoResolution、Tags |
| StageData | CurrentBatch |
| Episodes | BatchNumber |
| StoryboardFrames | BatchNumber |
| SeedancePrompts | LocalVideoUrl、BatchNumber、EpisodeNumber、UnitName、ShotLabel、ShotType、Duration、ReferenceImages、ReferenceVideos、ReferenceAudio |
| LLMConfigs | UpdatedAt |

这会造成项目创建、续写批次、视频设置、提示词生成、视频任务和自动增强等功能在新库上运行失败。

严重程度：**P0（运行时缺字段）**。

### 5.4 主升级脚本仍未覆盖完整结构

`Upgrade_补齐新表新字段.sql` 已覆盖一部分历史差异，但仍缺少：

- `Projects.CoverImage`、`StyleId`、`Tags`。
- `LLMConfigs.AutoEnhance`、`UpdatedAt` 的旧表补齐逻辑。
- `ReferenceAssets` 已存在但缺 `Tags`、`FileSize` 时的补齐逻辑。
- `VideoGenerationTasks.ResponseDuration`、`EnhanceDuration`、`EnhanceResolution`。
- 新增表的完整索引和外键补齐。
- 结构验证和失败中止机制。

严重程度：**P1；在特定旧库升级路径上可升为 P0**。

## 6. 运行时 DDL 架构问题

当前程序会在启动或业务请求期间执行建表、补字段：

- `Program.cs` 中包含多组启动时自动迁移。
- `DbService.cs` 在读取配置、视频任务、素材库、作品库等业务方法中调用多个 `Ensure...`。
- `VideoGenerationTasks` 至少存在多份重复建表定义，字段集合并不完全一致。
- 多处自动迁移使用空 `catch`，失败后不记录明确错误，应用可能继续启动，直到业务请求才暴露缺字段。

影响：

1. 应用账号必须长期保留 DDL 权限。
2. 第一次请求可能改变数据库结构。
3. 同一版本在不同机器上可能形成不同结构。
4. 迁移失败缺少可追踪记录。
5. 很难判断某个字段究竟由哪一份脚本负责。

目标状态：数据库结构由版本化脚本管理；业务运行账号只保留业务读写权限。运行时 `Ensure...` 在过渡期保留，待新库和历史库验证通过后再逐步移除。

## 7. 当前数据库的结构漂移

### 7.1 缺少预期外键

当前库中以下关系没有数据库外键约束：

- `Dramas.UserId -> Users.UserId`
- `Projects.DramaId -> Dramas.DramaId`
- `Projects.StyleId -> VideoStyles.StyleId`
- `EffectAssets.ProjectId -> Projects.ProjectId`
- `ReferenceAssets.UserId -> Users.UserId`
- `SkillLibrary.UserId -> Users.UserId`
- `Works.UserId -> Users.UserId`
- `VideoGenerationTasks.ProjectId -> Projects.ProjectId`
- `VideoGenerationTasks.PromptId -> SeedancePrompts.PromptId`

说明：不能直接在历史库上补外键。必须先检查孤儿数据、确认删除策略，再决定 `CASCADE` 或 `NO ACTION`。

### 7.2 缺少或不够严格的索引

当前需要重点评估：

- `Dramas(UserId)`
- `ReferenceAssets(UserId)`
- `SkillLibrary(UserId)`
- `Works(UserId)`
- `VideoGenerationTasks(ProjectId)`
- `VideoGenerationTasks(PromptId, CreatedAt)`
- `LLMConfigs(UserId, Provider)` 当前为普通索引，但代码逻辑假定每个用户、每个 Provider 只有一条。
- `StageData(ProjectId, StageNumber)` 当前为普通索引，但保存逻辑按唯一记录处理。
- `CoherenceChecks(ProjectId)` 保存逻辑按唯一记录处理，但没有唯一约束。

### 7.3 字段定义存在历史差异

示例：

- `Users.Nickname`：初始脚本定义为 `NVARCHAR(50)`，当前库为 `NVARCHAR(500)`。
- `ReferenceAssets`：当前库与升级脚本在文件名、类型、分类长度及日期类型上不同。
- `SeedancePrompts.UnitName`、`ShotLabel`：当前库长度小于主升级脚本的定义。
- `Projects.CurrentBatch`：当前库允许空值，代码虽然有默认回退，但目标基线应明确是否允许空。
- `VideoGenerationTasks.LocalVideoUrl`：不同建表来源分别使用 `NVARCHAR(500)` 和 `NVARCHAR(MAX)`。

历史升级只应执行安全扩宽和空值回填，不能直接缩短字段或强制非空。

## 9. Stage 11 专项规则

阶段编号是持久化 ID，不允许因为执行顺序而重排历史编号。

固定执行顺序：

```text
1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 11 → 9 → 10
```

Stage 11 规则：

- `11` 是后加入的特效资产阶段。
- 某些漫剧没有特效内容，因此 Stage 11 可以不存在，也可以为空。
- Stage 11 为空不能阻塞 Stage 9。
- 不对历史项目批量伪造 Stage 11 完成记录。
- 数据库基线只允许 `StageNumber=11`，不要求每个项目必须存在对应记录。

当前历史库的 Stage 11 记录数为 1；这符合“可选阶段”的历史现状，不是缺失数据。

## 10. 特效资产历史脚本风险

`Upgrade_特效资产表.sql` 同时包含两种职责：

1. 创建通用的 `EffectAssets` 表。
2. 针对指定项目和指定资产名称执行历史数据搬迁与删除。

通用结构迁移与特定业务数据修复不应放在同一份基线脚本中。后续处理时：

- `Baseline.sql` 只保留表结构。
- 特定项目的数据搬迁保留为已执行的历史迁移记录，不进入新环境基线。
- 不在当前数据库重复执行该段历史数据操作。

## 11. 建议的目标基线

### 11.1 兼容范围

首版基线以当前环境为下限：

- SQL Server 2016 或更高。
- 数据库兼容级别 130 或更高。
- 避免使用当前服务器不支持的新版 SQL 语法。

### 11.2 新环境基线原则

- 一份脚本包含当前代码所需的全部 21 张表。
- 明确每个字段的类型、长度、空值、默认值和标识列。
- 为常用用户、项目、提示词和视频任务查询建立索引。
- 对代码明确假定唯一的键建立唯一索引。
- 外键删除策略与业务删除流程一致。
- 不包含用户、API Key、连接串或特定项目数据。
- 建库失败时明确报错并停止，不静默忽略。

### 11.3 历史升级原则

- 执行前必须有备份或备份副本。
- 所有表、字段、索引和约束先检查再创建。
- 只增加、扩宽、回填，不缩短、不覆盖业务字段。
- 增加唯一索引前先检查重复数据。
- 增加外键前先输出孤儿记录数量。
- 发现不满足条件时停止并报告，不自动删除历史数据。
- 每个步骤写入可审计的执行结果。

## 20. 第六轮：L2 连续性表补入基线（2026-09-16）

### 20.1 触发原因

应用启动被 `DatabaseSchemaValidator` 拦截，报缺失 `dbo.ProjectContinuityTables`（整表缺失）。

根因是第 19 节确立的刷新流程没有被遵守：L2 连续性层只写了权威脚本 `ManhuaPipeline/Database/Upgrade_连续性表.sql`，**未同步进基线三个脚本**。于是启动报错的文案把用户指向 `Upgrade_Current.sql`，而当时的 `Upgrade_Current.sql` 里根本没有这张表——用户照做后仍然报错。这是**报错指引与脚本内容互相矛盾**造成的误导，比单纯缺表更难自查。

只读检查证据：

| 检查项 | 结果 |
|---|---|
| `ManhuaPipeline` 库 `dbo` 表数 | 41 张 |
| `dbo.ProjectContinuityTables` | `MISSING` |
| `dbo.AssetImageTasks` | `OK` |

`AssetImageTasks` 为 `OK`，说明历史升级脚本确实执行过，缺的只是本轮新增表。

### 20.2 补齐内容

| 脚本 | 本轮补齐内容 |
|---|---|
| `Baseline.sql` | +1 张表 `ProjectContinuityTables`（9 列、1 主键、2 索引）；建表段注释 7 → 8 张并标注各自同步日期；PRINT 表数 34 → 35 |
| `Upgrade_Current.sql` | 同内容的幂等建表段（`IF OBJECT_ID` 判定）；`UX_ProjectContinuityTables_Project_Type` 沿用"先查重复再建"策略，冲突时输出 P1 警告；版本号 2026-08-17 → 2026-09-16 |
| `Verify.sql` | 必需表 +1 项；必需字段 +9 项；索引检查 +2 项（唯一索引标 P0、普通索引标 P1） |

### 20.3 验证结果

在正式库补执行 `ManhuaPipeline/Database/Upgrade_连续性表.sql`（幂等，`IF OBJECT_ID ... IS NULL` 保护），执行后确认：

- `dbo.ProjectContinuityTables` = `OK`；
- 索引 3 个齐全：`PK_ProjectContinuityTables`、`IX_ProjectContinuityTables_Project`、`UX_ProjectContinuityTables_Project_Type`。

### 20.4 教训

新增 `ManhuaPipeline/Database/Upgrade_*.sql` 时，必须**同一轮**完成第 19.2 节的三步刷新，否则下一轮启动校验必然拦截，且报错文案会指向一个不含该表的脚本：

1. 跑 `Export_Schema.sql` 取最新结构；
2. 同步 `Baseline.sql`（建表段）与 `Upgrade_Current.sql`（幂等增量段）；
3. 同步 `Verify.sql` 的必需表 / 必需字段 / 索引清单。

> 最后更新：2026-09-10
> 维护说明：本仓库没有可用 git 历史（`.git` 仅为编辑器残留），代码备份只能靠 `bin` 构建产物和本目录文档。重大结构变更请先在这里留档。根目录历史构建残留（`build-*` / `.tmp_*` / `diagnose_*` 等）已于 2026-08-24 清理完毕，后续维护统一使用标准 `bin/obj`，不再在根目录新建临时构建目录。

## 1. 项目定位

ManhuaPipeline 是一套面向“漫剧”制作的 AI 生成流水线：从剧本出发，经过故事分析、全局蓝图、分集细化、导演层、分镜脚本、资产库、提示词生成，最终产出可交给视频引擎（Seedance 2.0 / ComfyUI / MediaKit）执行的提示词和参考图，并在系统内跟踪视频任务、Token 消耗与成品作品。

当前核心验证项目为《镇世武圣》第 1 季（项目 ID 30），重点验证打斗戏、角色资产、技能归属、导演层、战斗骨架、运镜原子、参考图自动绑定和 Stage 9 后置守卫等能力。

## 2. 核心链路

```text
剧本 → 创意构思/故事分析
     → 全局蓝图 → 分集细化
     → 导演层（整集导演计划 + 单元导演决策）
     → 分镜脚本（镜头规划，含打斗模板/技能锁定/时间轴/动作链）
     → 角色/道具/环境/特效资产 + 参考图资产（资产卡可一键出图，回填资产卡并同步进参考图库）
     → Stage 9 提示词生成（Seedance 提示词，含后置校验链）
     → 衔接检查 → 视频任务 → 轮询回写 → 画质增强 → 成品作品
```

数据流是逐级向下传递的：分集细化只吃剧本，分镜脚本吃分集细化 + 导演层 + 技能/模板/原子库，提示词生成吃分镜 + 全部资产 + 风格 + 技能/模板。上游缺失时下游只会越缺越多。

## 3. 阶段定义（PipelineStage）

阶段编号是持久化 ID，历史编号不允许重排。

| 阶段 | 名称 | 说明 |
| --- | --- | --- |
| 1 | 创意构思 | 剧本解析/创意构思 |
| 2 | 故事分析 | 故事结构分析 |
| 3 | 全局蓝图 | 整季/整集蓝图 |
| 4 | 分集细化 | 场景拆分，按集细化（温度固定 0.1） |
| 5 | 分镜脚本 | 整集导演 + 单元导演 + 镜头规划，锁定镜头描述、时间轴、技能、打斗模板、动作链 |
| 6 | 角色资产 | 角色卡提取（含战斗态、群像规则） |
| 7 | 道具资产 | 道具卡提取 |
| 8 | 环境资产 | 场景卡提取 |
| 11 | 特效资产 | 特效卡提取（编号 11，历史原因） |
| 9 | 提示词生成 | Seedance 提示词，逐单元增量入库 + 后置守卫 |
| 10 | 衔接检查 | 提示词之间的衔接检查 |

补充：**L2 连续性层不占阶段号**。它在阶段 3（全局蓝图）之后、阶段 4（分集细化）之前自动抽取六类连续性表（场景空间 / 角色连续性 / 道具状态 / 线索揭示 / 动作因果 / 转场动机），并作为阶段 4 的硬约束注入，因此阶段列表、进度体系与前端页面均不变。详见 `漫剧流水线架构合并方案-20260916.md`。

## 6. 账号、权限与配置

- 用户体系：注册 / 登录 / 个人中心，接口带 `SessionAuthorizeFilter` 会话鉴权。
- 页面 `config.html` 支持配置：
  - 大模型：DeepSeek、Qwen、ChatGPT（API Key / API 地址 / 模型名 / 思考模式）
  - 思考模式：DeepSeek 支持 `high / low / disabled`，直接映射到 `thinking: { type: enabled/disabled }` 或 OpenAI 风格 `reasoning_effort`
  - 当前启用的大模型 Provider（可选）
  - 视频生成引擎：火山方舟（云端 API）/ ComfyUI（本地工作流 JSON）
  - 火山方舟 API Key / 地址 / Seedance 模型名
  - MediaKit API Key（画质增强）与自动增强开关
  - 文生图中转 API（API Key / API 地址 / 模型名），供「资产卡出图」使用（Provider=`image`）
- `LLMService.CallAsync` 统一封装：按模型处理 `max_tokens`、思考模式；分集细化温度固定 `0.1`，受控打斗分镜 `0.4`，导演层 `0.2-0.3`，默认 `0.7`。

## 7. 剧集与项目管理

- `Projects`：项目主表，保存阶段进度、剧本内容、批次数。
- `Dramas` / `Episodes`：剧集与分集管理。
- `ProjectController` / `EpisodeController` / `DramaController`：项目、剧集、分集的创建与读写。
- 剧本续写：支持长剧本分段续写，缓解单次 LLM 输入过长、成本过高的问题。
- 进度：`StageProgressLogs` 保存阶段进度历史，前端可查看生成进度按钮与最新进度。

## 8. Stage 5 分镜脚本流程

Stage 5 实际是“整集导演 + 单元导演 + 分镜本体”三层接力：

1. 整集导演计划：`EpisodeDirectorPlanner` 按集生成整集导演计划（共 1 集 → 生成 1 份）。
2. 单元导演决策：`DirectorService.EnsureDirectorPlansAsync` 对每个单元生成导演决策，支持并行批处理（`Director:MaxConcurrency=5`），生成结果入 `DirectorPlans`。
3. 分镜本体按单元并行生成（`Stage5:StoryboardMaxConcurrency=4`），每个单元完成后通过 `onChunk` 增量入库，页面实时可见。
4. 文戏 / 打斗分流：
   - 文戏：自由分镜（`PlanShots`），输入单元文本 + 运镜原子菜单 + 技能库 + 导演决策。
   - 打斗：先由打斗意图提取器抽取意图，再由受控打斗分镜师生成，锁定模板、动作链、导演节拍、打包镜头与合规反馈。
5. `StoryboardAutoFixer` 对生成结果做后修正（缺镜头描述/时间轴等）。
6. 每次生成创建独立日志文件：`logs/storyboard_planning_p{pid}_s{stage}_yyyyMMdd_HHmmss_fff.log`，不再追加写同一个大文件。
7. 支持串行 / 并行两种运行模式（V4-3 后默认并行，单集内单元互不等待）。

## 9. 导演层（Director V1-V4）

| 模块 | 职责 |
| --- | --- |
| `EpisodeDirectorPlanner` / `EpisodeDirectorPlanParser` | 整集导演计划：情绪曲线、爽点、视觉预算、单元节拍安排 |
| `DirectorPromptBuilder` | 单元导演决策提示词：项目/风格/故事分析/总集蓝图/分集/前后单元/资产/技能/模板/运镜原子/战斗骨架/整集计划/上一单元状态快照 |
| `DirectorService` | 导演计划生成与并行调度 |
| `EpisodeStateSnapshotBuilder` | 单元结束状态快照，供下一单元衔接 |
| `EpisodeContinuityValidator` | 前后单元连续性校验 |
| `DirectorRuleValidator` / `DirectorSemanticValidator` | 规则校验 + 语义校验（默认开启，`Director:SemanticValidation.Enabled=true`） |
| `DirectorComplianceGuard` | 导演合规守卫：只限制不改技能，允许导演自行补充特效 |
| `DirectorRepairPlanner` | 校验不通过时的返工修复计划 |
| `DirectorValidator` / `EpisodeDirectorRuleValidator` | 导演结果结构校验 |

核心约束：导演可以自行加特效、加节奏，但不允许改技能归属和技能效果；镜头时长允许 5s / 11s / 15s 由 LLM 自行发挥，不做 5s 固定限制。

## 10. 战斗体系

- `FightTemplate`（打斗模板库）：按 T 层级 + 时长保存“适用 / 节拍 / 动作行 / 运镜行 / 约束行”，节奏总口诀“快—快—顿—重”。
- `FightArcTemplates`（战斗骨架库）：战斗段落总谱，例如 对峙 → 对话 → 接触 → 缠斗 → 升级 → 大招 → 胜负 → 切场；每个骨架带默认时长与阶段权重。
- `CombatActionCatalog` + `ActionChainBuilder`：动作链库与动作链组装（双方攻防回合序列）。
- `CombatIntentMapper`：打斗意图提取（1V1 / 1VN、主体、目标、升级路线）。
- `CameraAtom`（运镜原子库）：大远景、低角度极速推镜、贴身平行横移、特写锁焦、环绕跟拍等原子运镜。
- `ShotDirective`（分镜指令库）：镜头数量动态规则，按情绪/压迫 3-5 镜、对话 4-6 镜、普通战斗 5-7 镜、高速战斗 6-8 镜。
- `CombatGrammarCatalog` + `CombatGrammarEngine`：战斗语法库与语法引擎，用规则约束攻防回合表达。
- `CombatTimeBudgetBuilder`：按总时长分配各回合时间预算。
- `CombatWeightCalculator`：回合/技能/镜头权重计算。
- `CombatRuleEngine`：打斗规则引擎（受击反馈、禁止隔空比划、禁止命中无反馈等）。
- `ShotPacker`：把多个动作打包成镜头。
- `CharacterAliasCatalog`：角色别名目录（如 太虚圣主 → 七宗宗主等，用于技能/角色归属识别）。
- `CombatPlanSelector`：选择打斗模板并按技能归属过滤。

## 11. 资产库与参考图

- 四类资产：角色 `CharacterAssets`、道具 `PropAssets`、环境 `EnvironmentAssets`、特效 `EffectAssets`，均支持增删改查。
- `ReferenceAssets`：参考图资产，支持上传图片/视频，按标签管理。
- 角色卡规则：
  - 基础卡 + 战斗态卡：战斗/高潮/技能释放/战损镜头必须同时给“基础人物 + 战斗态”两张；非战斗镜头只给基础卡。
  - 群像：群像角色合并为一张群像卡，群像名必须与资产库一致（如 七宗宗主、宗门守山弟子群像）。
- 参考图自动绑定：Stage 9 生成提示词时按资产名自动生成 `@图N` 绑定行，页面按中括号 `[资产名]` 过滤文件名匹配参考图。
- 风格参考图固定名称“光影质感”，禁止 LLM 自创场景化风格名（冷月雨夜、葬天台冷暗光影等一律归一为 `[光影质感]`）。
- `PromptRefLineGuard`：只保留资产名单内的角色/战斗态/群像/道具/特效/技能/场景/风格卡，移除 LLM 自创且资产库不存在的绑定（如 `[旧灯]人物`），并统一补全“参考”二字。

### 资产卡出图（文生图，2026-09-12 新增）

资产卡（角色/道具/环境/特效）可一键出图，补上“资产卡必须先有图，视频才能拿它当参考图”这一环。

- 入口：项目页资产库每张卡右侧「出图 / 重新出图」按钮 → `POST api/project/{projectId}/asset/{category}/{assetId}/image/queue`（入队，由后台队列执行）。卡片状态位显示「排队中 / 出图中 Ns / 失败可重试」，页面每 3 秒轮询 `GET .../asset/image-tasks`，完成后自动刷新卡片。
- 批量出图：分类工具栏「批量出图」→ `POST .../asset/images/queue`，`scope=missing`（跳过已有图）/ `all`（全部重出）。
- 同步接口：`POST .../asset/{category}/{assetId}/image` 保留，请求内完成落盘与回填后返回，作兼容/回退用。
- 队列：`AssetImageQueueService`（`BackgroundService`）默认并发 3，配置键 `AssetImageQueue:MaxConcurrency`（钳制 1~8）；启动回收上次中断的任务，停机把执行中的任务释放回 `queued`；任务持久化在 `AssetImageTasks`（`Database/Upgrade_资产出图任务队列.sql`）。执行体 `AssetImageRunner.GenerateAsync` 同步接口与队列共用。
- 配置：`LLMConfigs` 用 Provider=`image`（配置页「图片模型配置 → 文生图（中转）」），填中转站 base 地址 + API Key + 模型名。地址只填域名会自动补 `/v1`，粘完整 endpoint 也能识别；接口形态不挑：先试 `/images/generations`，遇 404/405 自动回退 `/chat/completions`（兼容 gpt-image-1 / seedream / gemini-image 这类中转）。
- 提示词：资产名 + 描述 + 属性（角色卡）+ 项目画风（`VideoStyles.StylePrompt`）+ 类型固定要求（角色=单人全身纯色背景、场景=无人物空镜、道具=单体居中）。**「角色别名：xxx」这类行会被丢弃**——别名只服务 Stage 9 的 `[资产名]` 文本绑定，送进图像模型会被当成“要画出来的文字”。卡片弹窗里可临时覆盖提示词后再出图。
- 落盘与回填：`wwwroot/uploads/images/{projectId}/{资产名}_{时间戳}{ext}`，写回资产卡既有的 `ImageUrl` 字段（**不需要改表**）。
- 参考图库同步：生成图会**额外**存一份进 `ReferenceAssets`，`FileName` 直接取资产名——因为视频真正吃的是 `SeedancePrompts.ReferenceImages`，而它按「我的资产」图库的文件名匹配资产名（见上条“参考图自动绑定”），不同步的话出图等于白出。字段规则（2026-09-12 调整）：
  - `Tags` = **当前项目名称**；`Category`（图库「类型」，动漫/真人/游戏/仙侠）= 项目上设置的**资产库类型**（`Projects.LibraryCategory`，未设则回退成子类型）；`SubCategory` = 资产分类（角色/道具/环境/特效）。
  - 原实现把 `Category` 与 `SubCategory` **都**填成了“角色/道具/环境/特效”，所以图库「类型」从来没写对过，本轮修正。
  - 重新出图只删上一次**自动生成**的同卡图，靠 `ReferenceAssets.SourceKey`（`asset:{projectId}:{category}:{assetId}`）精确匹配，**手动上传的图不受影响**；早期没有 `SourceKey` 的历史记录按「自动出图」标签 + 文件名清理一次。
  - 项目「资产库类型」设置入口：项目页提示词页顶部「⚙️ 视频参数」条 → 「资产库类型」下拉，接口 `PUT api/project/{id}/library-category`（传空 = 清除）。
- 失败提示：两条路径都失败时，报错同时带两者的 HTTP 状态与响应原文，便于区分是中转地址、鉴权还是模型名写错。

### 关键帧层（L3 方案层，2026-09-16 新增）

每个**剧情节点**一张关键帧（8-16 张/集），把「角色站位 / 道具状态 / 场景朝向 / 线索可见性 / 镜头衔接」在节点上定死，作为分镜与视频生成之间的锚点。与上一节的「资产卡出图」是两条不同产线：资产卡是“一个资产一张”，关键帧是“一个剧情节点一张”。

- 表：`ProjectKeyframes`（权威脚本 `Database/Upgrade_关键帧层.sql`，**需手工执行一次**）。
- 选点是**系统确定性行为**（`KeyframePlanService.SelectCandidates`）：开场钩子 / 收尾悬念（P1）→ 状态锚点 / 信息增量 / 打斗节拍（P2）→ 单元首镜（P3），裁剪到 8-16 张；不足 8 张按均匀间隔补点；打斗单元取中段而非首镜。重跑结果稳定，不靠模型随手挑。
- 写细由模型完成（`LLMService.GenerateKeyframes`）：一次调用把每个候选节点写成构图 + 锁定项 + 图像提示词；数量对不上或调用失败的行自动降级为按分镜字段拼装（`Source=fallback`），页面照常可见。
- 入口：项目页左栏「关键帧」→ `keyframes.html`（按集分组展示，编号为**集内** `#1..#N`）；接口 `POST api/project/{projectId}/stage/keyframes/generate`、清空 `DELETE .../stage/keyframes`、只读 `GET api/project/{id}/keyframes`。
- 消费：阶段 9 按集注入【关键帧锚定】（`AgentService.BuildKeyframeAnchor`）。**未生成关键帧的项目，阶段 9 提示词逐字不变**（零回归）。
- 本版本**只做方案层**：不进出图队列、不写 `FrameAssetBindings`；后续若要真正出图并作为参考图回灌，需另开一期（会牵动出图队列与资产绑定）。

## 12. 技能库

- `SkillLibrary`：技能库条目，字段包含：技能名、系别、T 层级（T1-T5）、归属角色、标签、图片提示词、视频提示词。
- `SkillElements`：技能系别。
- 过滤逻辑：先按标签过滤，再按使用者（归属角色）过滤；不按项目名过滤，方便跨剧集复用。
- 技能库用途是“锁角色/锁技能”：Stage 9 只保留单元锁定技能，未锁定技能禁止出现在 `@图N` 行与正文。
- 分镜点名但库外无条目的技能：以分镜描述为准原样保留，不强制依赖技能库。
- 状态技例外：角色专属状态技（如 赤金气血）即使在非释放镜头，也可作为战斗态视觉锚定写入 `@图N`。
- 归属识别：通过 `CharacterAliasCatalog` 处理“七宗宗主 / 太虚圣主”“岳沉天（岳沉罡本体）”等别名，避免误判。

## 13. Stage 9 提示词生成

主流程（`AgentService.ChainGeneratePrompts`）：

1. 前置 5 次小调用，提取结构化输入：
   - 角色描述提取专家（角色资产 + 分镜）
   - 场景描述提取专家（场景资产 + 道具资产 + 分镜）
   - 道具描述提取专家（道具资产 + 分镜）
   - 特效描述提取专家（特效资产 + 分镜）
   - 镜头衔接分析专家（分镜）
2. 主生成角色：“你是一位好莱坞顶级影视提示词架构师 + 专业的 Seedance 2.0 视频生成提示词工程师”。
3. 逐单元生成，跑完一个单元立即 `InsertSeedancePrompts` 增量入库，页面实时可见。
4. 生成完成后对照 Stage 5 镜头数补漏：缺失单元自动补跑，重试 2 次仍缺才报错；补跑前按单元删除旧提示词避免重复。

输出模板（每镜头固定字段顺序）：

```text
【第X集】【单元X.Y】【镜头X.Y-Z】
类型:场景类型
@图1 [资产名]人物形象参考，保持外貌、发型、服装、气质一致；@图2 [资产名战斗态]战斗姿态参考；…（最多9段，最后一段固定 [光影质感]）
写实3D动画电影，4K，24fps，浅景深，无字幕无BGM，场景名+时间段
[0-3s]1组机位 + 1组核心动作 + 环境反馈
[3-7s]……
[7-11s]……
灯光：具体光源与受光对象
约束：正面要求
负向提示词：人物变形，手指畸形，画面闪烁，色彩混乱，字幕，文字，口型错误（最多补充1条特有项）
```

硬性规则：

- 总时长只允许 5s / 11s / 15s 三档；5 秒镜头 2-3 个时间块、11 秒 3-4 个、15 秒 4-5 个。
- 时间块用大块秒级区间（`[0-3s]`），禁止 `0-1s / 1-2s / 0-0.5s` 高密度小段，禁止块内再写子时间。
- 每个时间块只写 1 组机位 + 1 组核心动作，群像写整体趋势，禁止逐人复杂走位。
- 全部正文（含 `@图N` 行）控制在 500 个中文字以内；`@图N` 行单行控制在 180 字以内。
- 台词逐字照抄分镜原文，禁止改写人称/角色名；只有说话者标签（如 顾残山留音）允许规范化为正式角色名。
- 无台词镜头写“无台词，无口型表演，无对白”，禁止“语速无台词”这类矛盾表述。
- 内心独白格式 `内心独白-角色名:"内容"`，角色嘴巴闭合，不写口型同步；禁止“旁白/画外音”字样。
- 音效不单独输出字段，关键声音（拳风、闷响、碎裂）直接写进对应时间块正文；视频模型默认自动生成音效。
- 灯光行必须写具体光源与受光对象，禁止“主体亮背景暗”这类抽象词。
- 打斗镜头按动作链与回合数展开，禁止把多回合压缩成一次挥击+特效；命中瞬间可慢动作 0.2-0.4 秒，禁止整段慢放。
- 出拳要有蓄力→爆发→三层反馈（身体/环境/镜头），禁止拳锋未到敌人先倒。
- 站桩抵抗镜头写“双脚稳固、身躯不后退、不出手攻击、不倒地、不腾空”。
- 文戏节奏例外：分镜明确写快切/顿帧/情绪爆发时，即使类型为文戏也按节奏指令执行。
- 风格卡固定最后一段 `[光影质感]`，禁止 LLM 改写名称。
- 后期叠加（L5，2026-09-16 新增）：含手机短信 / 来电通话 / 新闻推送 / 文件信件 / 地图监控 / 公告榜单 / 报纸刊物 / 屏幕界面等文字元素的镜头，画面**只画洁净留白**，文字由后期叠加；信息靠人物反应与台词承载，禁止把文字内容写进时间块正文。规则原文由 `PostOverlayAnalyzer.RuleText` 单一来源提供，`PromptPostOverlayGuard` 把「视频中只保留屏幕留白，文字后期叠加」补进「约束：」行（幂等；已含原文则跳过），4 条守卫链全覆盖。
- 质感层（Mx-Shell 5 段，P3，2026-09-16 新增）：镜头/胶片锚点、光色锚点、材质锚点、瑕疵锚点、手持呼吸浮动、声音策略（无配乐仅现场同期声）、反空洞褒义词、收尾克制。**刻意不新增输出字段行**，质感锚点只写进既有行（时间块正文 / 灯光行 / 约束行），避免破坏 `SeedancePromptParser` `PromptRefLineGuard` 等守卫的解析契约。
- 关键帧锚定（L3，2026-09-16 新增）：项目生成过关键帧时，阶段 9 按集注入【关键帧锚定】，把该集的构图与锁定项作为硬约束；未生成则本条不出现，输出与改动前逐字一致。

### SSH 隧道连接细节（2026-09-10 更新到新实例）

服务器是 **Featurize 实例**，每重建一次实例，**SSH 端口与密码都会变**。

| 项 | 值 |
| --- | --- |
| 主机 | `workspace.featurize.cn` |
| SSH 端口 | `63542`（上一实例是 `34632`，换实例必改） |
| 用户 | `featurize` |
| 登录命令 | `ssh featurize@workspace.featurize.cn -p 63542` |

本地已配好的自动化脚本（都在 `C:\Users\power\.ssh\`）：

| 文件 | 作用 | 换实例要改什么 |
| --- | --- | --- |
| `featurize_reconnect.ps1` | **一键重连**：写密码、杀旧隧道、重建隧道、验证 | 不用改，值用参数传入 |
| `featurize_askpass.cmd` | 输出实例密码，供 ssh 免交互取用 | 由上面脚本生成，**不要手改** |
| `featurize_tunnel.cmd` | 建隧道 `本机 8188 → 实例 127.0.0.1:28490`，断线自动重连 | 由上面脚本生成，**不要手改** |

**换实例后只需一条命令**（`-Port` = 新实例 SSH 端口，`-Password` = 新实例密码，**两者每次换实例都会变**）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\power\.ssh\featurize_reconnect.ps1 -Port 63542 -Password <新实例密码>
```

它按顺序做 6 步：写 askpass（**先写临时文件**）→ **先试登录**（密码/端口错就在 ~1 秒内报错退出，
**不会动正在跑的隧道、也不改任何文件**）→ 杀旧隧道 → 重写 `featurize_tunnel.cmd` → 启动 →
轮询 `http://127.0.0.1:8188/system_stats`。实测全程 **约 4 秒**，隧道本身 1~1.5 秒起来。

也可以仍然直接运行 `featurize_tunnel.cmd`（它会 `set SSH_ASKPASS` 后起 ssh，所以
**必须跑这个脚本**，手敲 `ssh` 拿不到密码会一直等输入）；但它**不会**改密码/端口，
换实例后必须先跑 `featurize_reconnect.ps1`。

**两个容易踩的坑**

- 服务端 sshd 的 `AuthorizedKeysFile` 被改成了 `/home/featurize/work/.ssh/authorized_keys`（不是默认的 `~/.ssh/authorized_keys`）。
  往默认路径放公钥**不会生效**。而且这套方案用的是**密码 + askpass**，密钥认证实际没被使用
  （现有 `featurize_comfy` 密钥是加密的，`BatchMode` 下无法签名，服务端会先 `Server accepts key` 再 `Permission denied`，很容易误判成"公钥没配对"）。
- `~/work` 是 NFS 挂载且**内容很少**（换实例后基本是空的），**不要**把它当产物目录；ComfyUI 本体在 `/home/featurize/ComfyUI`，位于根盘 `/dev/vda3`。

### 服务器重启 / 更换实例检查清单（重要）

ComfyUI 服务器一旦重启或换实例，必须按下表处理。**核心风险：项目侧没有超时兜底**
（`GetProcessingPrompts` 只按 `Status IN ('processing','running','pending','enhancing')` 筛选，无时间过滤；
`ComfyService.QueryTaskByTaskId` 请求异常时返回 `"unknown"`，`VideoPollingService` 对 `unknown` 不做任何处理），
因此在跑的任务会**永久停在"生成中"，不会自动变成失败**。

先分清两种"重启"：

- **只重启 ComfyUI 进程**（实例没换）：SSH 端口不变，隧道一般不用动。
- **关掉实例、再开一个新实例**（Featurize 换实例）：**SSH 端口和密码都会变**（本次 `34632` → `63542`），**隧道必须重建**。

再按磁盘是否沿用分两类：

| 项目 | 磁盘沿用（Featurize 默认：实例重建、挂载盘保留） | 全新磁盘 / 换机型 |
| --- | --- | --- |
| 28490 → 本地 8188 映射 | **必须重建**（SSH 端口会变） | **必须重建**，端口可能又不同 |
| 服务器 `output/video` 里的视频 | **还在** | 丢失，没下载的找不回 |
| 服务器 `userdata/workflows` 工作流 | **还在** | 丢失（项目侧有副本，不受影响） |
| ComfyUI 队列、`/history`（进程内存态） | **清空** | 清空 |
| 自定义节点、权重文件 | 镜像自带，**还在** | 需重新准备 |
| 显存缓存 | 清空（好事） | 清空 |

> **2026-09-10 实测纠正**：Featurize 关实例再开，**磁盘是沿用的**——`/home/featurize/ComfyUI` 下
> `output/video` 里当天的 9 个 mp4、`userdata/workflows` 里 4 份工作流、权重、日志全都还在，
> 只有 ComfyUI 进程内的队列与 `/history` 丢掉了。
> 所以**"换实例产物全丢"的说法不成立，别急着重新生成，先去 output 里找**。
> 唯一麻烦是产物文件名（`MiniMax_H3_0000N_.mp4`）**无法反查回 `prompt_id`**：
> `comfyui.db` 只有资产表、没有 history 表；控制台日志（`~/ComfyUI/user/comfyui_28490.log`、`~/.apphub/comfyui.log`）
> 只记耗时与模型加载、不记文件名和任务号。因此**没有可靠的自动补下载手段**，只能按时间/内容人工判断。

**不用管的（项目侧自带，不依赖服务器）**

1. 工作流模板：本地 `wwwroot/uploads/comfyui/{userId}.workflow.json`，服务器 userdata 丢了也无所谓，不用重新导出。
2. 参考图：每次提交都会 `POST /upload/image` 重新上传，服务器 input 目录清空无影响。
3. 已下载视频：在 `wwwroot/uploads/videos/{projectId}/`，与服务器无关。
4. 显存：重启正好释放 ComfyUI 的模型缓存，反而更健康。

**必须处理的**

1. 地址/隧道：按上一节「SSH 隧道连接细节」更新 `featurize_askpass.cmd` 的密码与 `featurize_tunnel.cmd` 的端口，
   重建隧道后用 `Invoke-RestMethod 'http://127.0.0.1:8188/system_stats'` 确认能通；
   若新映射端口不是 8188，改 `LLMConfigs` 表 `Provider='comfyui'` 的 `ApiUrl`（项目里只有这一处存地址）。
2. **先去 output 里捞一遍**：换实例后磁盘沿用，`/home/featurize/ComfyUI/output/video/` 里可能已有
   一批生成完但没被下载的 mp4（本次 9 个）。**文件名无法反查 `prompt_id`，只能人工按时间与内容判断**，
   确认归属后再决定重跑哪些，避免白烧 GPU。
3. 卡住的任务：**最稳的是关实例前先在页面点「全部取消」**，让在跑任务状态落定；
   已卡死的，重新点生成，或手工把 `SeedancePrompts.Status` / `VideoGenerationTasks.Status` 从 `processing` 改为 `failed` 后再重提
   （`GetProcessingPrompts` 无时间过滤，卡死的任务会**永久卡在 processing**，不会自己变失败）。
   已知实例：`Id=1688`、`Id=1671`，以及 9-10 项目 44 批量提交的 `Id=1706~1720`（15 条）。
4. 服务器环境（换实例时逐项核对）：
   - 启动参数必须带 `--listen 0.0.0.0 --port 28490`（不 listen 0.0.0.0 隧道连不进来）。
   - 自定义节点：`MiniMaxH3ReferenceToVideo`、`ComfyMathExpression`、`ResolutionSelector`、`ComfySwitchNode` 均非内置，新实例没装则工作流提交即报节点不存在。
   - 权重文件：`minimax_h3_ref2va_int8_convrot.safetensors`、video vae（fp16）、audio vae（fp32）、`qwen3vl_32b_nvfp4_awq`、`ref2v_turbo_4step_v0.1`。历史上曾因缺 `minimax_h3_audio_vae_fp32.safetensors` 失败过。
   - 服务器 `userdata/workflows/` 下的工作流建议另存备份（项目不依赖它，但要在界面直接跑时需要）。

**重启后验证顺序**

1. `/system_stats` 能返回。
2. ComfyUI 界面上跑一遍 `video_minimax_h3_r2v`，确认自定义节点与权重齐全。
3. 回项目重提**一条**提示词，跑通 `/prompt` → `/history` → `/view` 全链路后再批量提交。
4. 轮询 60 秒一轮，提交后至少等 1 分钟。

**推荐操作顺序**：先在项目里全部取消 → 停服务器 → 换实例 → 补自定义节点与权重 → 建隧道 → 确认 `/system_stats`
→ 清理残留 processing 任务 → 重提一条验证 → 再批量提交。

## 23. 已知问题与边界

- 打斗戏效果仍需打磨：当前“时间块 + 动作链 + 模板”已能产出多回合交锋，但相比手搓提示词的极速节奏仍有差距；Seedance 2.0 时间戳是时序提示而非剪辑时间线，切换点有 ±1s 浮动，0.5s 级爽感需拆短片段后期变速实现。
- 提示词长度：官方建议中文 ≤500 字，超过会忽略细节；当前生成含 `@图N` 行常接近上限，仍需持续压缩。
- LLM 生成不稳定：同一输入多次结果可能不同；已用温度、规则和校验器约束，仍存在返工。
- 参考图按字符串匹配：资产名若含相同字符串会锁到同一张图；中括号 `[资产名]` 过滤已缓解，但资产命名仍需唯一规范。
- 长剧本成本高、耗时长；已通过并行分镜、进度日志、思考模式 low/disabled 和续写模式缓解。
- VS 构建偶发文件占用错误（`rpswa.dswa.cache.json` 被另一进程使用、`AssemblyReference.cache` 拒绝访问），通常是 VS/后台服务占用了 `obj`，关掉重复进程或重启 VS 即可。
- 没有可用版本历史，代码回滚困难；建议尽快引入 git，或将关键节点打成 zip 备份。历史构建产物（`build-*` / `.tmp_*`）已删除，不要再依赖它们做备份。
- 阶段并发保护是单进程级，多实例部署时需升级为分布式锁。
- 校验器语义校验可能误报（别名识别、起始/结束画面等），需要持续校准。
- 文生图单张几十秒（中转站高峰排队更久，`HttpClient` 超时放宽到 10 分钟）；已改为后台队列 + 批量入队（默认并发 3），不再长时间占着页面请求。队列是**单进程内存级调度**，多实例部署时需换成数据库分布式抢单（当前已用乐观更新抢单，扩展成本不高）。
- 出图提示词只由「资产名 + 描述 + 属性 + 项目画风」拼成，**不含分镜上下文**，所以同一资产在不同镜头的光影/构图差异仍只能靠视频侧提示词控制，不能指望出图阶段区分。
- 资产卡出图依赖“图库文件名 = 资产名”这一约定（与参考图自动绑定同源）：**资产改名后旧的自动生成图文件名不会跟着改**，会匹配不上，需要重新出图；同理两个不同资产重名会互相串图。（图库侧自动图的去重已改用 `SourceKey`，不受资产改名影响。）
- `ImageServiceTests.DefaultSizeFor_UsesWideSizeOnlyForScenesAndEffects` 的期望值与现行实现不一致：`ImageService.DefaultSizeFor` 现在四类统一返回 `1280x720`，该用例待校准。
- 出图队列、`AssetImageSupport`（提示词拼装与图库同步）、`AssetImageRunner` 目前没有单测，抢单与停机回收逻辑建议后续补用例。
- 关键帧层（L3）目前**只做方案层**：不进入 `AssetImageTasks` 出图队列、不写 `FrameAssetBindings`；若要真正出图并作为参考图回灌视频阶段，需另开一期（会牵动出图队列与资产绑定）。关键帧是**人工触发**：不点生成按钮时 `ProjectKeyframes` 为空，阶段 9 提示词与改动前逐字一致。
- 后期叠加与质感层是**纯提示词层**改动：不新增输出字段行（避免破坏 `SeedancePromptParser` 与既有守卫的解析契约），只把约束写进「约束：」行、把质感锚点写进既有行。
- 基线三脚本（`Baseline.sql` / `Upgrade_Current.sql` / `Verify.sql`）本轮新增段落只做过 `PARSEONLY`，空库与还原副本实测仍待补（见 `database_baseline/README.md` 与 `数据库基线整理记录.md` 第 19-21 节）。
